# Phase 3A executable shadow candidate

The candidate is `../phase2/shadow-workflow.candidate.yml`, outside active workflows. Every execution step invokes implemented code. Default admission is closed by `admission-root.closed.json` and the absence of independently protected owner pins. No hosted shadow run or deployment is authorized by this implementation.

The job graph is admission → actual complete collection/plan → worker-0, worker-1, worker-2 in parallel → independent advisory aggregation. Workers are separate jobs, with individual service-owned output channels; failure does not cancel siblings. The existing sequential Public Safety workflow, stable mandatory-evidence context, source/security/governance workflows and all historical checkpoint/financial pins remain unchanged. Shadow coverage never grants merge readiness.

## Implemented commands

`python -m tools.ci_v3_hosted_controller` implements `admit`, `pull-image`, `plan`, `worker`, `outputs` and `aggregate`. Each stage requires `--root`, its independently retained `--root-sha256`, and `--output`. Workers additionally require `--project` and `--worker`. Run/attempt identities come from the host Actions environment and are reconciled with live service metadata. Incomplete stages write rejection evidence and return nonzero.

The controller reuses the Phase 1 planner and Phase 2 report producer, JUnit bridge and independent verifier. Schema 1 is unchanged. Schema 2 remains the compatibility layer. Schema 3 adds pinned admission, host receipts, transport provenance and explicit isolation constraints. The optimized exact-byte Git source check uses one archive operation instead of thousands of Git subprocesses and refuses omitted/nonregular tracked content.

`python -m tools.ci_v3_prepare --project REPOSITORY --output NEW_EXTERNAL_DIRECTORY` performs only actual collection, never test execution. It writes a current inventory, collection/process/environment evidence, node-count proxy weights, empty nonpass policy and blocked isolation decisions. It requires clean committed source and an external new output directory. Preparation on Windows is explicitly not the independently approved Linux/image inventory. It does not hardcode the historical test count or approve observed skips. Review runtime skip/xfail policy separately using exact original node IDs and reasons; never bless newly observed failures/skips automatically.

## Protected host and test container

Trusted host code is checked out at the independently admitted controller revision, verified against its tree and every Python tool hash. It never imports subject tests on the host. Subject code executes in the admitted immutable image as the host's numeric non-root UID/GID, with no external network, no capabilities, no new privileges, a read-only image/bootstrap, private tracked source/history, private evidence and tmpfs, 512 PID and 6 GB memory limits. A narrow allowlist passes only nonsecret CI identity and deterministic native-thread settings. GitHub tokens, artifact runtime credentials, job output files, host home and Docker socket are not mounted or forwarded. Subject Git configuration is replaced with a credential-free local configuration; public history/refs remain for historical guards. A standalone full-history source checkout is required.

The host observes the Docker CLI exit, enforces a finite budget, captures original child evidence and independently seals the host receipt after container completion. It compares the private tracked source bytes/executable bits, Python file set and HEAD/ref identity before/after execution without running Git against subject-modified configuration. It explicitly removes its uniquely named container and verifies absence; killing the CLI process group alone is insufficient. A removal timeout still runs process-group cleanup; daemon failure cannot establish container absence. Cancellation triggers the same cleanup; service cancellation, missing uploads, source mutation and unproved cleanup fail. Disposable hosted runners remain the final cleanup boundary if the host itself is forcibly terminated. This design does not call same-user local pytest processes a security sandbox. Docker/runner/image integrity and protection from hostile co-tenants remain Security Owner assumptions.

## Integrity and authenticated provenance

The verifier's independent inputs are the protected owner root, trusted host job outputs delivered through `needs`, and live read-only GitHub metadata. Adjacent receipt JSON and artifact names cannot authorize anything. Original artifact ID, archive digest, host receipt hash and job ID are retained outside the test container before being consumed by downstream jobs. Upload action outputs provide service artifact identity/digest; a separately computed host receipt hash anchors the original observation.

The transport uses GET only, fixed GitHub HTTPS origin, bounded pagination/download/expansion and explicit redirect allowlists. API credentials are not forwarded to blob storage. It validates current run attempt, workflow ID/path/revision/content, repository, tested commit/tree, controller tree, job identities/conclusions, exact artifact set, archive digests, artifact lifetime and expected job interval. Archive extraction rejects raw/normalized path changes, traversal, alias paths, duplicate names, symlinks and oversized/incomplete transfers. Native JUnit and every required adapter/process/finalizer artifact must match the independently anchored host receipt.

GitHub's artifact API supplies run identity and digest, but does not provide an uploader job ID. Job association therefore rests on protected host job outputs plus the pinned workflow/controller and container credential boundary; artifact names or timestamps alone are insufficient. Do not substitute a worker-generated JSON list for `CI_V3_HOST_ANCHORS`. The CLI obtains that channel from the pinned workflow's `needs` expressions. It has no offline JSON metadata success switch.

TLS/service retrieval authenticates service provenance under those trust assumptions; SHA-256 and CRC establish ordinary byte integrity. They are not owner signatures, proof of financial correctness or merge approval. Mock service integration explicitly returns `provenance_authenticated=false` and `provenance_mode=mock-service`. Non-container synthetic execution is an internal test seam only, unavailable through the hosted CLI and forbidden from claiming hosted authentication.

Primary service contracts: [Actions runs](https://docs.github.com/en/rest/actions/workflow-runs), [jobs](https://docs.github.com/en/rest/actions/workflow-jobs), [artifacts](https://docs.github.com/en/rest/actions/artifacts), [upload action outputs](https://github.com/actions/upload-artifact#outputs). Live read-only preflight also checks actual response fields; no service job-artifact relation is invented.

## Admission still required

Owners must supply an exact protected environment root and controller pin, an immutable reviewed execution image with resolved dependency evidence, independently approved complete current inventory/policy/runtime weights, exact module/shared-fixture isolation decisions, and separately approved workflow deployment. No image is built/published and no environment/root is enabled here. The root references an immutable Git approval bundle, not worker-selected files. PR source and synthetic merge parents/tree must remain identical throughout the experiment. Main-head runs must match independently observed main.

Local Windows validation exercises actual tiny processes and the full transport/coverage chain with mocked service metadata. Real Linux/POSIX tests are platform-gated and must pass in exact-head existing CI. Mock Docker lifecycle tests exercise normal/nonzero/timeout/finalizer/leak/cancellation/cleanup failures without claiming an actual container run. A real approved container/image execution remains a separate authorized prerequisite; this implementation does not manufacture that evidence.
