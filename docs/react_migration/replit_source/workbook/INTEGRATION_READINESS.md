### Canonical authority, save/run, access and feature gates

- The browser UI is never the source of truth for a production model. A production server must authorize project access, validate inputs against a canonical schema, enforce feature gates and decide whether each user may read, edit, save, run, approve or export.
- A real editable cell must carry a stable field/period identity, unit, allowed precision/range, editability state, and an explicit expected Working Copy revision. Save should submit an atomic batch against that revision and return the committed revision; a revision mismatch must reject the whole batch and offer reload/compare rather than silently overwrite.
- Save and Run are separate commands. Save acknowledgement is not a run; a run must return a persisted Run ID linked to the exact committed input revision/hash, engine/model version, user, timestamp, and status. A statement is `CURRENT` only when its persisted input revision matches that run's revision; otherwise show `STALE` or `UNKNOWN`.
- Existing sandbox keyboard edits, validation, query context, demo session storage and synthetic IDs are not API contracts. No route, endpoint, payload, permission or database fact has been verified from the original app.
- Feature gates must be authoritative server policy, not a disabled-looking client-only control. Storage, files, exports, audit evidence and lender approvals require explicit permissions and server-side checks.

## Architecture options for a future existing-FINCO integration

This is a conceptual comparison using the user's supplied app context only. The current server-rendered architecture, reusable components, API surface, auth model and release topology were not inspected in this design project; validate them with the actual owners before choosing.

| Option | React reuse / workflow fit | Adapter, lifecycle and security | Performance, testing and maintenance | Assessment |
|---|---|---|---|---|
| **A · Port the visual structure to FastAPI/Jinja2/HTMX** | Recreates the shell and forms in server templates; little direct reuse of React grids | Server forms fit existing request/permission boundaries, but period-grid keyboard/paste behavior must be reimplemented; HTMX swaps need clear target/state ownership | Smallest frontend runtime, but duplicate interaction logic and separate grid tests; high risk of inconsistent keyboard contracts | Lowest integration risk only if the current server UI is intentionally staying entirely server-rendered |
| **B · Existing server shell with selective React islands** | Reuse the complex Input/CAPEX/OPEX/statement grids while retaining server-rendered pages and simpler forms | Add a narrow adapter to the existing canonical server contract; define HTMX mount/unmount cleanup, state handoff, CSRF/session behavior and CAS rejection handling; server remains authorization and persistence authority | Limits migration surface; test React island behavior plus HTMX lifecycle and server integration; moderate maintenance | **Provisional recommendation for a first PoC**, subject to confirming the current shell can host islands safely |
| **C · Full React frontend against existing FastAPI** | Highest reuse of the React mockup and shared components across the full model flow | Requires stable APIs for every module, auth/session/CSRF design, explicit CAS semantics and an adapter for legacy routes; risk of duplicating permission/business rules | More consistent SPA navigation, but largest test, performance, accessibility, deployment and maintenance scope | Consider only after an API contract and ownership decision supports a broader frontend migration |

### Prioritized conceptual implementation roadmap — no repo or GitHub changes made

1. **Contract and authority discovery:** with owners, verify the actual existing UI shell, auth/permission model, canonical input/output schema, existing save/run flows, CAS/revision mechanism and test infrastructure. Do not infer these from the sandbox.
2. **Narrow architecture PoC:** in an approved branch/repo, connect exactly one editable scalar input to the existing canonical Save with revision/CAS and permission checks; separately read one persisted statement row/view with its source Run ID and engine version. Keep Run execution out of the PoC unless the established contract explicitly supports it.
3. **Truthful stale/current evidence:** test a second input revision, stale statement handling, denied permissions and concurrent edits; show `CURRENT` only for matching persisted input/run evidence and use `UNKNOWN` otherwise.
4. **Grid island decision:** only after the PoC, measure a period-grid adapter with internal scrolling and keyboard/paste validation, including HTMX mount/unmount tests if option B is chosen. Compare maintenance/performance results before expanding.
5. **Module-by-module gate:** extend PPA, CAPEX/OPEX, financing, credit and analysis only with verified server contracts, authority, tests, feature permissions and explicit provenance.

## Integration guardrails

1. Treat all displayed numbers, dates, histories, checks, comparisons and trace rows as synthetic fixtures until an authoritative model-run source is explicitly connected and verified.
2. Keep local draft Save, persisted model Save, model Run, output freshness, integrity checks and credit approval as separate states. Do not infer one from another.
3. Do not introduce guessed endpoint paths, request/response shapes or database fields from this design-only inventory.
4. Preserve period, unit, facility, contract, scenario and statement context as navigation metadata only; query parameters do not persist or authenticate model data.
5. Before any production integration, agree on an authoritative schema, validation, save atomicity, run identity, provenance contract, permissions and evidence for each destination with the product/backend owners.

### PoC pass/fail gate

Before implementation, a separately authorized GitHub task must verify the real app shell/HTMX version, field registry and units, canonical validation and Save boundaries, revision/CAS behavior, auth/CSRF, read-only persisted statement source, feature-flag mechanism, exact-head CI and staging-approval process. If any are unknown, stop at discovery and report evidence; do not invent endpoints or an adapter contract.

The PoC passes only if the real server atomically saves one permitted existing input against an expected revision, rejects invalid/unauthorized/stale writes without partial changes, and exposes one persisted statement tied to a real Last Run. Show `CURRENT` only for matching revision/run evidence; otherwise `STALE` or `UNKNOWN`. Save must not call Run. Keep the flag off by default and the existing route as fallback. Require exact-HEAD CI, permission/CAS/freshness/no-auto-Run tests, an independent read-only review, and owner-authorized staging acceptance. Roll back by disabling the flag and retaining the existing route; no migration or engine changes belong in this PoC.
