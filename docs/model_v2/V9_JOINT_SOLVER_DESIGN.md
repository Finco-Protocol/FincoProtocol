# V9 joint numerical candidate: architecture and authority boundaries

Base: `5996453b8d5bbfaa48bc06922fc6963cf94d2f84`, merged PR #325.
This is candidate development, NOT financial approval or a released optimization.

## Default execution

Normal `run_clean_production` never imports the V9 candidate entry. All default
hooks are `None`. The entire `run_project_financing_model` G2A function remains
AST-identical to the immutable base, including every intermediate capacity pass,
the original zero seed, strict service-budget refinement, all financial checks
and exception precedence. There is no B1 deferral, analytic D seed or BG secant.
No change to the Senior solver, tax engine, period engine or a financial tolerance.

The application extracts its existing maturity/metadata/statements/developer
assembly into one shared helper. It does not introduce another financial engine
or a second statement calculation. Every default output, not only KPIs, is tested
against actual immutable-main results.

## Proposal-only entry

`financial_engine.financing.v9_candidate.evaluate_candidate` is a laboratory
entry, not a router, worker, input field, environment switch or saved configuration.
Its three approval/activation constants remain literal `False`; the production
activation function always refuses. The candidate is not used for a committed
Run or historical export.

The reduced vector is six-dimensional:

`(Senior IDC, commitment fee, structuring fee, VAT IDC, VAT fee, initial DSRA)`.

Its components are computed by the existing Stage B2 and H-1 target authority.
Anderson type-II proposals use depth two, finite/nonnegative/step-bound checks,
history reset after inadequate residual reduction and a terminal plain-Picard
phase. These are proposal safeguards, not new financial acceptance tolerances.
There is a maximum of 15 joint outer transitions after the neutral seed, plus
the unchanged final verification; exhaustion
returns control to the original canonical Run. The existing outer residual,
strict Stage B2, unfunded check, idempotence verification and final DSRA test remain.

The six-vector history is request-local. No new global cache, cross-Run seed or
cross-tenant numerical memory exists. Guarded execution joins the existing
`engine_run_scope` so already approved exact-input operating/tax memoization can
reuse immutable subresults; it adds no new memoized function or equivalence key.

## Financial composition

The candidate evaluates the existing construction loop with an explicit local
context and consumes its result once through the existing shareholder waterfall.
`FinancingBinding` binds the complete typed input bytes, source and baseline;
different inputs, source, baseline or financing-income vector refuse reuse.
U2 reserve-income configurations, typed Junior/multi-Senior extensions,
quarterly projects and cases without both H-1-derived construction and DSRA are
not optimized. They retain canonical execution. Quarterly acceptance tools invoke
the existing isolated engine composition, never product admission or activation.

No monetary field is replaced by a residual plug, rounded to a golden, or clamped
to obtain convergence. Contractual financing, SHL maturity, tax, statements and
returns are still calculated by the original kernels.

## Rejection authority: not solved by a final check

Keeping G2A checks at every visited iterate is necessary but does not prove
equivalent coverage of *outer* iterates skipped by the joint trajectory. A
successful final proposal is not proof that the original path would succeed.

Therefore guarded mode **always executes the original canonical Run**, even when
the proposal succeeds, and returns the original result or original exception.
It never promotes a successful proposal over a rejected baseline. Unexpected
proposal errors are separately recorded, not treated as approval. Complete
re-decision has a measured cost and is included in guarded performance results.

An executed control records the actual Solar canonical and joint Stage B2
configuration trajectories, selects a configuration visited only by the canonical
trajectory, and injects a synthetic `residual=11.25 kEUR` refusal at that exact
configuration. Actual canonical execution rejects; actual raw joint execution
returns a proposal; guarded execution rejects with the identical canonical error.
This is a deterministic **injected control-flow counterexample**, not evidence
of a real economic input defect. It shows why a final convergence test or
exception-only fallback cannot justify dropping the canonical re-decision.

`verify_canonical=False` exposes a clearly labelled NON-AUTHORITATIVE proposal
only for OD-1 field comparisons and raw timing. Raw proposal speed is NOT an
accepted production speedup. There is no proven bypass-eligible production subset.

## Provenance and governance

The original research branch is read-only historical input. No branch merge,
cherry-pick, runtime source compilation or global monkeypatch is used.
The protected manifest records exact predecessors and proposed Git blobs, with
every approval state false. New negative controls check proposal bytes only.
They are deliberately not wired into historical frozen-namespace guards.
Existing RC-7C, M7, F3, WF-04, Revenue and PPA authorities remain unchanged.

An independent successor must be reviewed separately before it can affect any
existing guard. RC-7C D-01 through D-12 and quarterly activation remain untouched.
